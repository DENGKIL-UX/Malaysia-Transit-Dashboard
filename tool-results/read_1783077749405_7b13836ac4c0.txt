   233→## Why Prasarana Can't Just Use the API
   234→
   235→data.gov.my has NO REST API for Prasarana daily totals. Tested all variants:
   236→- `ridership_prasarana_daily` → 404
   237→- `ridership_rapid_rail` → 404
   238→- `ridership_od_rapidrail_daily` → 404
   239→
   240→Only KTMB (`ridership_ktmb_daily`) and Headline (`ridership_headline`) have REST APIs. Prasarana OD data is ONLY available as bulk parquet downloads.

   242→## Why the Badge is Misleading
   243→
   244→In `/api/metadata/route.ts` lines 316-326, `freshest_date` is the MAX across 4 candidates. The GitHub metadata date (2026-06-30) wins because it's the newest, but no chart ever reads from it.

   246→## D1 Feasibility
   247→
   248→**YES — D1 is a good fit.** Free tier (5M reads/day, 100K writes/day, 5GB) is far more than sufficient.
   249→
   250→Architecture: Separate Cron Worker fetches parquet → parses → upserts into D1. Dashboard API routes read from D1 instead of static JSON.
   251→
   252→Challenges: (1) CF Workers can't run Python/pandas for parquet parsing — need parquet-wasm or GitHub Actions runner, (2) CF Pages Functions don't support cron — need a standalone Worker, (3) Free tier 10ms CPU may be tight for 2.2MB parquet parse.
   253→
   254→Simpler alternative: GitHub Actions cron → runs `process_parquet.py` → commits new JSON → triggers CF Pages rebuild.
